# CLAUDE.md

Compact day-to-day guidance. **Deep architecture, pipelines, rationale, and Dialog/Sheet quirks live in `plan/CLAUDE_ARCHIVE.md`** — consult before changes that touch data flow, pipelines, or window-based UI.

## Repo layout
- `app/` — Android app (Kotlin/Compose), package `com.librelookai`.
- `firebase/` — Cloud Functions (`geminiProxy`, `verifyPurchase`, pricing trigger) + Firestore rules.
- `scripts/` — Python/shell helpers (`add_translations.py`, `translation_status.sh`, `kt_split.py`).
- `plan/` — long-form docs: `CLAUDE_ARCHIVE.md`, `FIN.md`, `TODO.md`, `TRANSLATION.md`.
- `designs/` — design-handoff bundles (HTML mockups, JSX prototypes, per-surface `README.md`).
- `website/` — static marketing site (vanilla HTML/CSS + `i18n.js`/`translations.js` in 12 languages; real-device screenshots in `screenshots/`).
- `README.md` (root) — Firebase / signing / partner-program setup.

## Model & effort
- **Sonnet** for routine work · **Haiku** for trivial lookups, boilerplate, formatting · **Opus** for hard architecture or debugging.
- Use low effort for straightforward tasks to save tokens.

## Working agreement
- **Ask before `git commit`**; never commit without explicit approval.
- **Update CLAUDE.md / `plan/CLAUDE_ARCHIVE.md`** when architecture, data flow, or conventions change — both before executing a plan and after it lands.
- **Multi-language is mandatory.** Every user-facing string goes through `stringResource(...)` + `res/values/strings.xml`, mirrored into every `values-*/strings.xml` in the same change. Never hardcode display text.
  - Bulk insert: `scripts/add_translations.py <batch.json>` writes `{locale: {key: rawValue}}` into each `values-*/strings.xml` (auto XML-escape, idempotent). Audit coverage: `scripts/translation_status.sh`.
  - After either, run `./gradlew :app:assembleDebug` — `mergeDebugResources` validates XML + format specifiers across all 31 locales.
- **Release notes** ship with every Firebase / Play release; bump `versionCode` and refresh notes together.
- Keep tasks small; read files and follow existing patterns before editing.

## File size & splitting
**Aim ≤ 500 lines per `.kt` file (target 300–500).** Soft limit: a *single cohesive* composable that legitimately dominates a file (e.g. `WardrobeGrid.kt`'s `GridContent`) may exceed; a *cluster* of many functions over 500 still gets split. Apply the **Placement rule** to decide where the extracted symbols land.
- **Screens** — keep the entry-point `*Screen` composable in the original file; extract groups into siblings (`<Feature>Cards.kt`, `…Dialogs.kt`, `…Sheets.kt`, `…Viewer.kt`) in the **same package** so `internal` visibility and Robolectric tests keep working.
- **ViewModels** can't be sliced arbitrarily. Move pure data / UI-state to `data/model/` or `<Feature>Models.kt`; extract self-contained workflows (audit, import, fix-scans, dedupe) into same-package `internal fun ViewModel.x()` extensions the VM delegates to. Don't break tested public/`internal` signatures (`*Content` composables, `TagFilterBar`, etc.). Verify each extraction with `./gradlew :app:assembleDebug`.
- Tooling: `scripts/kt_split.py` (`split` / `add_imports` / `qualify`) mechanizes same-package extraction — its docstring is the how-to. Compiler is the source of truth: extract → `compileDebugKotlin` → bump flagged privates to `internal` / add flagged cross-package imports → repeat.

## Build & test
- `./gradlew assembleDebug` — debug APK.
- `./gradlew testDebugUnitTest` — JVM unit tests. Bare `./gradlew test` rejects `--tests`; use the variant task to filter.
- **Cut a release**: `scripts/release.sh <versionName>` — bumps `versionCode`/`versionName`, prepends notes to `release-notes.txt` (via `$EDITOR`, `--notes <file>`, or stdin), builds the signed APK, commits + tags `vX`, uploads to the Firebase App Distribution `testers` group, and (with `--push`) pushes. `--dry-run` shows the version+notes diff and reverts; needs a clean tree. Full release / function deploy → `plan/CLAUDE_ARCHIVE.md` § Release process.
- **JVM tests**: plain JUnit for pure logic (`TagNormalizerTest`, `PHashTest`). **Compose flow tests** run on JVM via Robolectric (`createComposeRule()` + `@RunWith(RobolectricTestRunner)` + `@GraphicsMode(NATIVE)`) — see `wardrobe/TagFilterBarTest`. Test the **`internal`/stateless `*Content` composables** (`TagFilterBar`, `TagEditScreenContent`, …) with **hoisted state**, not whole screens (screens default their ViewModels to `viewModel()` and do real Drive/Gemini/ML I/O). Resolve display text via `getString(R.string.…)`, not literals.
- **JDK gotcha**: Robolectric can't instrument under JDK 25. Tests are pinned to a **Java 21 toolchain** (`tasks.withType<Test>` in `app/build.gradle.kts`; path in `gradle.properties` → `org.gradle.java.installations.paths` → Homebrew `openjdk@21`) — foojay auto-download is incompatible with Gradle 9. `testOptions.unitTests.isIncludeAndroidResources = true` lets `stringResource` resolve.
- **Instrumented tests** (`androidTest/`, needs device/emulator): `./gradlew connectedDebugAndroidTest`. Prefer Robolectric; reserve instrumented for true device-dependent paths. Cross-tab nav can only be exercised by launching `MainActivity` (tabs are a single `selectedTab` inside the root NavHost's Home destination).

## Package layout (under `com.librelookai`)
`MainActivity` at root. Feature packages: `auth/`, `onboarding/` (first-run tour — `OnboardingScreen` + `OnboardingState`), `wardrobe/` (incl. `LocationViewModel`, `CaptureScreen`, `UrlImportPicker`, `WebProductFetcher`, `WardrobeGap*`), `outfit/` (incl. `PredictionSetupScreen`, `OutfitCalendar`), `travel/` (`TripsViewModel`, `TripViewerScreen`), `tryon/`, `shopping/`, `billing/`, `settings/` (single flat package; live UI is `SettingsScreen` + the `*Card.kt` / `*Dialog.kt` / `*Screen.kt` siblings; `ProfileViewModel`, `UserPreferences`, `AppLanguage`, `AppFont`, `UsageScreen`/`UsageCostsTab` also live here. `FixCutoutBgDialog.kt` is still hosted by `MainActivity`). The former `insights/` package was dissolved — see Navigation. Cross-cutting: `data/model/` (pure data), `data/drive/` (`DriveRepository`), `data/local/` (Room: `LocalDatabase`, `WardrobeItemStore` + impl, Hilt module), `gemini/` (`GeminiRepository`, `PromptStore`, `ApiKeyStore`, `TokenUsage*`, `TagNormalizer`), `ml/` (`EmbeddingService`/`…Repository`/`…Index`, `SegmentationRepository`, `PHash`, `ColorHistogram`), `weather/`, `service/` (`JobForegroundService`), `util/` (`Analytics`, `NetworkUtils`, `Scrollbar`, `AiProcessingOverlay`), `ui/theme/`.

**Placement rule (cohesion over locality).** Put each new or moved file in the package with the **most in-package callers and fewest cross-package callers**.
1. List which existing symbols it calls and which existing files call it.
2. Pick the package that maximises same-package edges and minimises `import com.librelookai.<other>.…` lines.
3. If used by ≥ 2 feature packages with no clear owner, lift to `data/model/` (pure data), `util/` (no-dep helper), or the relevant cross-cutting package. Don't dump in `util/` just to avoid choosing.
4. Avoid creating a new top-level package for a single file — extend an existing one unless ≥ 3 related files justify it.
- Wrong-placement symptom: the new file's `import com.librelookai.…` block is longer than its body, or it adds reverse-direction imports (e.g. `data/model/` importing from a feature package). Move it.

## Dependency injection (Hilt)
- Hilt (KSP) is wired in: `LibreLookAIApp` is the `@HiltAndroidApp` Application, `MainActivity` is `@AndroidEntryPoint`. Versions: Hilt 2.59.2 + KSP 2.3.9 — AGP 9's built-in Kotlin needs Hilt ≥ 2.59 and KSP (kapt is incompatible).
- **`DriveRepository`, `GeminiRepository`, `GoogleAuthManager` are `@Singleton` `@Inject constructor` classes — never construct them by hand.** ViewModels receive them as constructor params (`@HiltViewModel class X @Inject constructor(app: Application, …) : AndroidViewModel(app)`); composables get them threaded down as parameters (`AppContent(activity, driveRepository)`).
- Plain `viewModel()` call sites keep working unchanged — the `@AndroidEntryPoint` activity's default factory is Hilt's, and it falls through to the regular factory for un-annotated VMs. ViewModels with no injected deps stay plain `AndroidViewModel(app)` until they grow one.
- Repository *interfaces* (for fake-based tests) are deliberately deferred to refactor phase 2 — see `plan/refactor.md`.

## Core conventions
- **Identity is `folderId`** — closets map to Drive subfolders. `Location.id` is an ephemeral UUID and must never be used for identity comparisons.
- **File naming triplet**: `{cutoutDriveId}_cutout.webp`, `{cutoutDriveId}_original.webp`, `{cutoutDriveId}.json` — sidecar shares the cutout's Drive ID. Legacy `_cutout.png` / `_original.jpg` items still load (no Drive-side rewrite).
- **Image encoding is centralised in `util/ImageEncoding`** — both cutout and original are written as **WebP** to keep the user's Drive small (target ~1 GB for thousands of items). Quality follows the user's `UserPreferences.imageQuality` tier (Settings ▸ Advanced; BALANCED=lossy q80 default, HIGH=q90, MAXIMUM=lossless), mirrored into the static `ImageEncoding.tier` by a `LaunchedEffect` in `AppContent` (same pattern as `EmbeddingService.segmenter.foregroundThreshold`). **Never `bitmap.compress(PNG/JPEG, …)` for a stored cutout/original** — call `ImageEncoding.compressCutout`/`compressOriginal`. **Never `name.endsWith("_cutout.png")`** — use `ImageEncoding.isCutoutName` / `isOriginalName` / `cutoutIdFromName` (accept both new + legacy suffixes); build new Drive names with `cutoutNameFor`/`originalNameFor` (or `DriveRepository.CUTOUT_SUFFIX`/`ORIGINAL_SUFFIX`, which now delegate to WebP). Local cache filenames stay opaque keys (decoders sniff magic bytes). Gemini-bound image bytes are labelled by `ImageEncoding.detectMimeType` (sniffs the real format — Gemini accepts `image/webp`), not by file extension. Drive uploads send `image/webp`.
- **Shopping closet** lives in `LibreLookAI/_shopping/`; excluded from `Location` lists, included in cross-closet similarity snapshot.
- **Offline gating**: read `LocalIsOffline.current` and either hide write-path UI or set `enabled = !isOffline`. Every Gemini / Drive-write surface must be gated.
- **Optimistic writes**: mutations (move / delete / tag-edit / bg-queue persist) update in-memory state immediately and write the local cache **before** the Drive call (in the same background coroutine, ahead of the Drive ops); Drive syncs after and rolls back on failure. **The wardrobe item cache is Room** (`data/local/WardrobeItemStore`, one `@Singleton` shared by Wardrobe / Outfits / Shopping VMs — the old per-folder `wardrobe_cache_*.json` files are seeded into it once on upgrade, then never read again). **Cache-folder rule**: key every cache write off the item's *owning* `folderId`, never the transient active-filter `folderId` (null in All-locations, changes on closet switch) — use the VM helpers (`persistItemToCache` / `addToCacheFile` / `removeFromCacheFile`, now suspend), don't rebuild a folder cache from the whole `state.images`. The store's primary key is the Drive ID, so **an item is homed in exactly one folder** — upserting under a new folder atomically re-homes it (moves can't leave ghosts). Invariants are tested in `data/local/WardrobeItemStoreTest`. **The outfit cache is Room too** (`data/local/OutfitStore`, seeded once from the old `styles_cache_*.json`): rows hold the `Outfit` as opaque Gson JSON keyed by outfit id, so **an outfit is homed in exactly one folder** (the old files duplicated fresh empty-`folderId` outfits into every folder's cache), and reads restore the `@Transient Outfit.folderId` from the row; the create/edit save paths stamp `folderId` so a fresh outfit homes correctly before the next Drive sync. Outfits still call `refreshOutfitsLocalCache()` (now suspend, over the store) after each mutation. Invariants in `data/local/OutfitStoreTest`. **The remaining JSON caches are Room as well**: calendar wears in `data/local/OutfitEventStore` (per-folder, keyed by event id, seeded once from `outfit_events_cache_*.json` incl. the legacy `styleId` alias; `OutfitEventsViewModel.persist()` keeps Drive-first ordering), trips in `data/local/TripStore` and try-on metadata in `data/local/TryOnStore` (both single global lists with a one-row seed marker, seeded once from `trips_cache.json` / `tryons_cache.json`; try-on **image bytes stay files** in the Drive cache dir — the store holds metadata only, and `TryOnViewModel.migrateSource` applies on store reads as on Drive reads). All legacy JSON files are left on disk as a downgrade net. Invariants in the matching `data/local/*StoreTest` suites. Rationale → `plan/CLAUDE_ARCHIVE.md` § Two-phase load / Optimistic writes.
- **Lazy grids**: never leave a persistent `graphicsLayer`/transform on a `Lazy*` container — it makes the grid skip composing items that appear after a data swap ("items missing until you scroll"); gate it behind the active gesture (see `WardrobeZoomableItemGrid`). Give `items`/`itemsIndexed` a stable `key` **and** `contentType`.
- **Gemini calls return `null` on failure** — every caller must degrade gracefully. All calls log via `TokenUsageRepository.recordUsage(...)` with a `UsageCategory`.
- **AI progress overlay is data-driven.** `util/AiProcessingOverlay` (the gold sparkle shown by every AI-trigger surface) collects the global `gemini/GeminiProgress` bus: it shows the **real upload-byte bar** while the request body streams (driven by `GeminiProgress.CountingRequestBody`), then a **time-based wait estimate** asymptoting toward ~95% (Gemini answers in ~20–40s), plus an elapsed-seconds counter (`ai_progress_*` strings). The bus is wired once via the `GeminiProgress.Listener` `EventListener` on `GeminiRepository.http` (call start/upload-end/finish) — no per-call-site changes; it's a single global slot, so an overlapping bulk call (no overlay) may overwrite it harmlessly.
- **Fashion trends are cached, not fetched per call.** `gemini/FashionTrendsCache` wraps the expensive Google-Search-grounded `searchFashionTrends` with a **weekly, location-specific** cache: keyed by normalised region string, served local-disk-first (`filesDir/trends_cache.json`) → shared Drive (`_trends_cache.json` at root, so reinstall / 2nd device reuse it) → only a genuine miss/stale (> 7 days) hits Gemini, then writes back to both. Falls back to a stale entry on Gemini failure. Both outfit prediction & composer go through `OutfitsViewModel.trendsCache.get(region, category)` — don't call `gemini.searchFashionTrends` directly.
- **Calendar wear history is a taste signal.** Each `OutfitEvent` carries a denormalised snapshot taken at wear time (`outfitName`/`outfitTags`/`itemTypes`/`colors`/`aesthetics` + `tempC`/`weatherCode` + `source` (`WearSource.MANUAL`/`AI_SUGGESTED`) + `loved` + `planned`) so the wear stays usable even after the outfit is edited/deleted — every field has a default so Gson back-fills old events via the generated no-arg ctor. `outfit/WearHistory.kt` owns it: `buildOutfitEvent(outfit, imagesById, source, weather, date)` builds the snapshot (future date ⇒ `planned`), `buildWearHistorySummary(events)` condenses it into a wear-weighted prompt block (manual = ×2, loved = +3; recent wears flagged "avoid repeating"; cold-weather lean called out). The prediction, composer **and** travel-packing prompts all append it. `OutfitEventsViewModel.recordOutfit(outfit, imagesById, source, weather)` (not an id any more) + `setEventLoved(eventId, loved)` are the writers; the calendar day sheet has a ❤️ toggle. History reaches the prompt via `OutfitsUiState.wearHistory`, kept in sync by a `LaunchedEffect` in `AppContent` (the two VMs are independent); the travel planner reads the same `OutfitsViewModel` state and threads it through `buildPackingPrompt`. Gated by the `AiConsiderations.history` toggle (default on; `ai_consider_history` row in `ConsidersCard`, and a chip in the travel planner's `AiConsidersChips`). The travel planner also exposes the expert item-tag dimensions (`AiTagChips`, mirroring the composer's `ExpertTagsCard`). `OutfitEventsViewModel.setEventLoved(eventId, loved)` toggles the loved flag on **one** logged wear — the per-wear ❤️ on the calendar **day sheet** (`OutfitEvent.loved`), and the only thing feeding the taste signal's loved weighting. Hides offline.
- **The outfit ❤️ is one favourite, shared across all outfit-centric views.** `Outfit.loved` (persisted in `_outfits.json`, Gson back-fills `false`) is the outfit's own favourite flag, settable *before it is ever worn*, toggled via `OutfitsViewModel.setOutfitLoved(outfitId, loved)` (optimistic + multi-folder save, mirrors `setOutfitTags`). It backs the ❤️ on the **outfit list card** (`OutfitCard`), the **fullscreen detail viewer** (`OutfitFullScreenViewer`, top-right) **and the wear-stats tab** (`OutfitWearStatsTab` reads `style.loved`) — so the heart stays in sync everywhere. It is distinct from the per-wear `OutfitEvent.loved` (day sheet), a finer "loved this specific wear" signal. There is exactly **one** `setOutfitLoved` (on `OutfitsViewModel`); the old events-VM `setOutfitLoved` was removed. All ❤️ affordances hide offline.
- **`Outfit.loved` is its own AI taste signal — NOT tied to wear history.** `buildLovedOutfitsSummary(styles, imagesById)` (`outfit/OutfitsPrompts.kt`) emits a "## Favourite outfits" block (loved outfits' names + tags + item types/colours) appended to the **prediction, composer and travel-packing** prompts, independent of `buildWearHistorySummary`/the `AiConsiderations.history` toggle. Prediction also stamps `"loved":<bool>` onto each entry in its styles JSON so the model can prefer a loved outfit by id. Composer takes a `lovedOutfits` param (callers pass `s.outfits.filter { it.loved }`); prediction/travel derive it from the `styles` they already receive. Always on when any outfit is loved.
- **"Wear" picks the day in the calendar, not a date-picker dialog.** The outfit list card and fullscreen viewer's wear action (label `outfits_wear` + trailing chevron) no longer open a dialog — they call `OutfitsViewModel.requestCalendarWear(outfitId, source)` and switch to the Outfits ▸ **Calendar** sub-tab, where the user taps the wear day in context of their previously-worn outfits. `OutfitCalendarTab` resolves the pending request (`pendingCalendarWearId`/`pendingCalendarWearSource`) into the calendar's **pick mode** and consumes it (`consumeCalendarWear`). The post-save snackbar still logs "Wear today" (`outfits_wear_today`) directly. The trip detail viewer (`travel/TripViewerScreen`) keeps its own `WearDatePickerDialog` (still defined in `OutfitCard.kt`) since cross-tab nav from the Travel tab would be jarring.
- **Calendar "pick mode" (`outfit/OutfitCalendar.kt`, `CalendarPick`)** replaced every Material `DatePickerDialog`/`WearDatePickerDialog` in the calendar: while a wear/move/copy is pending, the **month grid itself is the date picker** — a prompt banner shows at top (`calendar_wear_prompt` / reused `calendar_move_prompt` / `calendar_copy_prompt` + Cancel), every day cell is tappable to complete the action, and the day sheet / `AppFab` / `SelectionActionBar` are suppressed (Back cancels). Tapping a day runs the wear/move/copy and shows a `SnackbarHost` confirmation (`calendar_done_wear`/`_move`/`_copy`). Entry points that set `pickMode`: the day sheet's per-event Move/Copy, the long-press selection bar's day Move/Copy, the "Log outfit" FAB's context-less add (→ `Wear`), and an external `requestCalendarWear`. `onAddOutfit` carries a `WearSource` so list/AI-suggested wears keep their provenance.
- **Long-press any day — empty *or* filled — raises the shared bottom `SelectionActionBar`** (`selectedDays`). A single selected day shows **Add outfit** (`calendar_add_to_day`, primary; `addOutfitForDate` → `OutfitPickerDialog` titled `calendar_add_pick_for`, logging straight onto that day with a snackbar) plus **Copy · Move · Remove** when that day already has outfits; multiple selected days drop Add (it's single-day only) and keep **Remove** only (Remove appears only when some selected day actually has outfits). Tapping more days in selection mode toggles them in/out via the shared `selectDay` helper, whose rules: **outfit days multi-select; empty days are single-select and never coexist with outfit days** (selecting an empty day replaces the selection unless an outfit day is already selected, in which case it's a no-op; selecting an outfit day replaces a lone empty selection else adds). Re-selecting an already-selected day unselects it **unless it's the only one selected**. A plain **tap** on a filled day still opens the read-only day sheet (`selectedDate`, per-event love/wear-again/move/copy/remove/edit); tapping an empty day does nothing. Because the month grid is fixed-height (the pager has `weight(1f)`, not a scrollable list with bottom `contentPadding`), the calendar `Column` carries a bottom inset (`gridBottomInset`): at rest a small `CALENDAR_GRID_BOTTOM_INSET` (28.dp) so the last week row only just overlaps the floating weather badge instead of hiding behind it, and while a selection is active the measured selection-bar height (`onSizeChanged` → `selectionBarHeightPx`) instead, compressing the grid up so every day stays visible/tappable above the bar. Keying the choice off `selectedDays.isNotEmpty()` (not the stale measured height) means it snaps back to the small inset the instant selection clears.
- The `MonthHeader` has a **"Today"** `Icons.Default.Today` icon button just left of the month label (`calendar_today` content description); it animates the pager back to `MONTH_PAGE_ANCHOR`.
- **Prompt wardrobe encoding** is centralised in `DriveImage.toPromptJson(c, includeName)` (`wardrobe/PromptItemJson.kt`); every prompt builder (prediction, composer, gap, replacements, travel packing) routes items through it — don't hand-roll the JSON. Which tag dimensions are emitted is the user's `AiConsiderations.itemTags` "expert" choice (`null` = all, back-compat default; `type`/`category`/`name` always sent). Surfaced as `ExpertTagsCard` in the shared Tune-AI sheet (per-invocation override) and `ExpertTagsStrip` in `ProfileEditScreen` (saved default); gap analysis reads the saved default.
- **Colors are a closed vocabulary.** `gemini/TagNormalizer.CANONICAL_COLORS` (35 values) is the only source of truth; `String.normalizeColor()` snaps every color — Gemini output, manual "add custom" input, and filter/display reads — onto it (known synonyms map to a sibling, anything else → `multicolor`), so no swatch-less color is ever stored. The Edit-Tags color picker / filter swatches (`wardrobe/WardrobeColorSwatches.FilterColorKeys` + `colorSwatchHex`) only render canonical keys; `TagNormalizerTest` asserts the display list and canonical set stay in sync. Other tag dimensions (type, material) remain open free-text. The classify prompt lists the same set as a hard constraint.

## Navigation
- `MainActivity` is a thin `@AndroidEntryPoint` `ComponentActivity` whose `onCreate` just calls `AppContent(activity, driveRepository)` (`AppContent.kt`). The whole composition (auth gate, all VMs, the root NavHost, global dialog hosts) lives there.
- **Root NavHost (Navigation Compose, type-safe `@Serializable` routes in `AppNavigation.kt`).** `HomeRoute` = the tabbed Scaffold — still a single `selectedTab: Int` + `when(selectedTab)` dispatch, sub-tab reset via `navResetTick`. Converted full-screen screens are **sibling destinations overlaying Home** (covering the bottom bar); `TripViewerRoute(tripId)` is the first — the old hoisted `tripViewerTripId` mode in `TravelScreen` is gone, `onOpenTrip` navigates (`launchSingleTop`), system back pops. `TravelPlannerRoute` followed — the hoisted `travelPlannerMode` flag (and its `hideChrome` arm) is gone; `travel/TravelPlannerScreen` owns the planner-lifecycle effects (packing-list → trip auto-create, source-closet seeding, `navigateToTrip` collection) because the Travel tab is not composed while the planner overlays Home, and a planner-created trip pops back to Home before navigating to the trip viewer. `OutfitViewerRoute(source, outfitIds, initialOutfitId, tripId)` converted the three `OutfitFullScreenViewer` Dialog hosts (outfit list / prediction result / trip day list): the viewer is a plain fullscreen composable now, rendered by `outfit/OutfitViewerDestination`, which resolves outfits **live** from the VMs per source (`list` = route ids in filtered display order; `prediction` = `predictionSuggestions` — every close path clears the prediction so Home's navigate trigger can't re-fire; `trip` = the trip's day list, so a day-edit's id swap stays in sync) and hosts the viewer-launched tag-edit/suggest dialogs plus the trip wear-date picker (the launching surface underneath isn't composed while the destination overlays it). The Outfits screen flips to its Calendar sub-tab via a `pendingCalendarWearId` `LaunchedEffect`, so viewer-destination wears land in calendar pick mode. Remaining Dialog-viewers convert one at a time (plan/refactor.md phase 3). Transition-period rules:
  - **Global overlay hosts live outside the NavHost** (try-on + outfit composer Dialogs, Quick try-on sheet, prediction setup, replacements result, AI-notice/credits dialogs, `FixCutoutBgDialog`, restore overlay) so they keep working over any destination. `LocalBgRemovalScreen` is the exception — it stays inside Home's content Box (won't surface while a destination overlays Home).
  - **Tab jumps from global hosts / CompositionLocals go through `goToTab(tab)`** (pops back to `HomeRoute` first) — a bare `selectedTab = X` would switch tabs invisibly under an overlaying destination.
  - **Every destination pins `CompositionLocalProvider(LocalViewModelStoreOwner provides activity)`** and passes the activity-scoped VMs to its screen explicitly: inside a destination, a defaulted `viewModel()` resolves against the back-stack entry and silently forks a fresh VM. Per-destination VM scoping happens deliberately, one converted screen at a time.
- **Entry gate** (`AppContent.kt`, top-level `when`): `showOnboarding -> OnboardingScreen` | `!isSignedIn -> SignInScreen` | `else -> full app`. The onboarding tour is the **outermost gate on first run** — it now owns Google Drive sign-in + background-permission setup, so it renders **before** the sign-in check. `SignInScreen` is only reached by returning users who signed out *after* completing onboarding. `profileViewModel`, `networkMonitor`/`isOffline`, `selectedTab`/`navResetTick` and `showOnboarding` are hoisted above the gate so onboarding can use them; the OAuth machinery (`authorizationLauncher`, `pendingAuthIntent` + `attemptFirebaseSignIn` `LaunchedEffect`s) already lives at the top, so onboarding only calls `authViewModel.startSignIn()` and reacts to `isSignedIn`.
- **First-run onboarding**: a `showOnboarding` flag (seeded from `onboarding/OnboardingState.isComplete`, persisted in its own SharedPrefs file) drives an opaque fullscreen `OnboardingScreen`. A swipeable `HorizontalPager`: value-prop / feature pages → **Connect Google Drive** (`DriveSignInPage`) → **Allow background processing** (`BackgroundPermissionPage`) → **Enable location for weather** (`LocationPermissionPage`, optional) → **Gemini API key** (`ApiKeyPage`) → style profile → try-on photo → finish. Profile/photo come *after* Drive sign-in because they write to Drive. **Mandatory-first is what makes prefill safe**: a `LaunchedEffect(isSignedIn)` reloads the account's saved `UserPreferences` from Drive the moment sign-in lands (the first-run `ProfileViewModel.init` load failed pre-sign-in), so an account that already has data (reinstall / new device) prefills the style/profile steps, and `finish()` *merges* the three edited fields (`gender`/`yearOfBirth`/`preferences`) into the loaded prefs instead of overwriting theme/language/AI options with defaults. `finish()` only persists when online **and** `!state.isLoading`. The onboarding branch in `AppContent` is wrapped in its own reactive `LibreLookAITheme(paletteId = profileState.preferences.wardrobeTheme, …)` (same pattern as the main-app branch, overriding the cached outer theme), so a saved palette/font **re-skins the tour live** the moment that reload lands; `profileState` is hoisted above the entry-gate `when` for this. **Three required steps** (no top-right **Skip**, **Next** soft-blocked until satisfied): Drive sign-in (until `isSignedIn`), background processing (until `PowerManager.isIgnoringBatteryOptimizations`, re-checked on `ON_RESUME`; the global battery `AlertDialog` in `AppContent` stays as a safety net), and the API key (until `startsWith("AIza")` & len ≥ 30, persisted live via `ApiKeyStore`). The location step is **skippable** — `ACCESS_COARSE_LOCATION` via `RequestPermission`, re-checked on `ON_RESUME`; powers weather-aware suggestions; `AppContent` still requests it post-onboarding as a safety net for returning users. ## Close / back affordance rule
**Position is fixed at top-left/leading; the glyph encodes the relationship.** A hierarchical drill-down that returns to a parent in a back-stack (Settings sub-routes, `ProfileEditScreen`, `TagEditScreen`, `AboutScreen`) uses `Icons.AutoMirrored.Filled.ArrowBack` + `R.string.action_back`. A self-contained modal / fullscreen task that dismisses back to its launcher (capture, similarity, composer, pickers, viewers, planner) uses `Icons.Default.Close` + `R.string.action_close`, always top-left (leading in a header `Row`/`TopAppBar`, or `.align(Alignment.TopStart)` in a `Box`) — never bottom, never a FAB. The dismiss cross's *position* must not change between states of the same screen (`CaptureScreen` keeps its top-left close in both capture and import-FAB modes). `action_cancel`/`action_dismiss` are reserved for non-navigational uses (aborting an in-progress edit, dismissing a banner); chip-remove / text-clear / Edit↔Close toggles keep their own `Close` glyphs and strings.

## Window quirks (Dialog / Sheet / Popup / AlertDialog)
**Every composable that opens its own window** (`Dialog`, `ModalBottomSheet`, `Popup`, `AlertDialog`, `BasicAlertDialog`, and anything nested inside one) severs the locale-overridden `LocalContext` / `LocalConfiguration` chain and reports `WindowInsets.systemBars` as 0.

Rule of thumb:
1. Capture `parentContext` / `parentConfiguration` **outside** the window-opening call.
2. Re-provide via `CompositionLocalProvider` **inside** the content lambda (for `AlertDialog`, inside **each slot lambda** — the outer wrap doesn't reach slots).
3. Use `LocalSystemBarsPadding` (provided high in `AppContent`) instead of `statusBarsPadding()` / `navigationBarsPadding()` inside Dialogs.
4. Sticky bottom rows in fullscreen Dialogs: `effectiveBottom = max(LocalSystemBarsPadding bottom, view.rootWindowInsets systemBars bottom, 48.dp)`.
5. Fullscreen `Dialog` (not inline composable) is how a detail view overlays the bottom nav bar.

Full rationale + reference implementations (`OutfitComposerScreen` slot-dialog helper, `WeatherPickerSheet`/`ClosetPickerSheet` ModalBottomSheet pattern, `FullScreenViewer` Dialog wrap, `MatchPreviewDialog` action row) → `plan/CLAUDE_ARCHIVE.md` § "Compose Dialog quirks". Read it before adding any new window-based UI.

## Monetization (coins + BYOK)
- **Master switch: `billing/ManagedBilling.enabled`** (← `BuildConfig.MANAGED_BILLING_ENABLED`, set from `managed.billing.enabled` in `local.properties`, **default `false`**). Off = BYOK-only release: every coin/purchase/refinancing surface is hidden (AI-credits card + section, Buy-credits packs, coin cost badges, spend confirms, destructive-dialog coin row), the Gemini proxy is never used (`GeminiRepository.isProxyMode`/`isConfigured`), `CreditRepository.isManagedMode()` is false, and `CreditsViewModel` never connects to Play billing. BYOK key entry stays in **Settings ▸ Advanced** (and the bottom of `BuyCreditsScreen`). Flip the flag (with a deployed proxy + Play products) to light the coin economy back up with no code change. The Play release ships with it off. First-run onboarding includes a **"Add your Gemini API key"** step (`onboarding_apikey_*` strings; deep-links to AI Studio key + billing pages, paste field, Next soft-blocked until a key is entered) — see Navigation. End-user walkthrough: `docs/GEMINI_API_KEY.md`. **Two tiers**: a free key covers tagging/suggestions; virtual try-on + background removal generate images and need a billing-enabled (paid) key — the old "free key avoids all costs" copy was corrected across `about_byok_*` / `settings_advanced_byok_*`.
- **Pricing is server-authoritative.** Firestore holds `config/pricing` (private: `multiplier` + raw `costs`) and `config/publicPricing` (auth-readable: post-multiplier coin prices). The `recomputePublicPricing` trigger is the only writer to `publicPricing`. The multiplier never reaches the client.
- **Client reads `config/publicPricing`** via `gemini/PricingClient` (Firestore listener + SharedPrefs cache + fallback to `CreditPack.COST_*`). Started once in `MainActivity.onCreate`.
- **Cost UI**: `billing/CostBadge` is a small leading icon (`🪙 N` managed, `~Nk tokens` BYOK, hidden otherwise) — place it as the first child of any AI-trigger button. `ConfirmSpendDialog` + `requiresSpendConfirm()` gate spends ≥ 20 coins or bulks ≥ 5 items (BYOK never gated).
- **402 → typed exception + global event**: `GeminiRepository.throwIf402` parses `{needed, have}`, emits on `billing/CreditsEvents.topUp`, then raises `billing/InsufficientCreditsException`. A single `InsufficientCreditsDialog` observer in `MainActivity` listens and routes "Buy" → Settings — so individual VMs don't manage dialog state. Per-VM catches only reset loading flags and short-circuit bulk loops via a local `creditsExhausted` flag.
- **No-key / failed-call → global `AiNotice`**: `gemini/AiEvents` (mirrors `CreditsEvents`) carries an `AiNotice(kind, messageRes, canRetry)`. Every repo call funnels through `ensureConfigured(notify)` (emits `NOT_CONFIGURED` when no key/proxy) and `emitFailure(code, body, notify)` (maps 429→quota, 400+`API_KEY_INVALID`→invalid key, 403→permission/paid-key, 5xx→server, blocked/empty 200→blocked, else generic). **Emission is gated on `notify`** — only **user-initiated single calls** pass `notify = true` (`tryOnOutfit`, composer `generateText`); automatic/bulk calls stay silent and degrade to `null` as before. A single observer in `AppContent` shows one `AlertDialog`: `NOT_CONFIGURED` → "Set up key" (closes the try-on/composer Dialogs, jumps to Settings tab 5); `FAILED` → reason + "Retry" when the trigger registered one. **Retry** re-runs the *whole* originating op via the `AiRetry.action` holder, which the trigger site sets right before launching (only single user-tapped actions register; bulk leaves it null → reason-only dialog). `buildRequest`'s managed-no-session path emits `FAILED`/`ai_unavailable`; methods catch `AiUnavailableException` separately so it isn't double-emitted.
- **Ledger**: every charge/refund/purchase appends to `users/{uid}/ledger/{autoId}` (server-only write, user can read).
- **`verifyPurchase`** validates against the Google Play Developer API before crediting; the service account needs "View financial data" + "Manage orders" in Play Console.
- **Seeding**: `cd firebase/functions && npm run build && node lib/seed.js` writes initial `config/pricing` (defaults in `firebase/functions/src/pricing.ts → DEFAULT_PRICING`); the trigger mirrors to `publicPricing`.
