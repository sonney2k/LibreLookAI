## Working agreement
- **Ask before `git commit`**; never commit without explicit approval.
- **Update CLAUDE.md / `plan/CLAUDE_ARCHIVE.md`** when architecture, data flow, or conventions change — both before executing a plan and after it lands.
- **Multi-language is mandatory.** Every user-facing string goes through `stringResource(...)` + `res/values/strings.xml`, mirrored into every `values-*/strings.xml` in the same change. Never hardcode display text.
  - Bulk insert: `scripts/add_translations.py <batch.json>` writes `{locale: {key: rawValue}}` into each `values-*/strings.xml` (auto XML-escape, idempotent). Audit coverage: `scripts/translation_status.sh`.
  - After either, run `./gradlew :app:assembleDebug` — `mergeDebugResources` validates XML + format specifiers across all 31 locales.
- **Release notes** ship with every Firebase / Play release; bump `versionCode` and refresh notes together.
- Keep tasks small; read files and follow existing patterns before editing.

## File size & splitting
**Aim ≤ 500 lines per `.kt` file (target 300–500).** Soft limit: a *single cohesive* composable that legitimately dominates a file (e.g. `WardrobeGrid.kt`'s `GridContent`) may exceed; a *cluster* of many functions over 500 still gets split. Apply the **Placement rule** to decide where the extracted symbols land.
- **Screens** — keep the entry-point `*Screen` composable in the original file; extract groups into siblings (`<Feature>Cards.kt`, `…Dialogs.kt`, `…Sheets.kt`, `…Viewer.kt`) in the **same package** so `internal` visibility and Robolectric tests keep working.
- **ViewModels** can't be sliced arbitrarily. Move pure data / UI-state to `data/model/` or `<Feature>Models.kt`; extract self-contained workflows (audit, import, fix-scans, dedupe) into same-package `internal fun ViewModel.x()` extensions the VM delegates to. Don't break tested public/`internal` signatures (`*Content` composables, `TagFilterBar`, etc.). Verify each extraction with `./gradlew :app:assembleDebug`.
- Tooling: `scripts/kt_split.py` (`split` / `add_imports` / `qualify`) mechanizes same-package extraction — its docstring is the how-to. Compiler is the source of truth: extract → `compileDebugKotlin` → bump flagged privates to `internal` / add flagged cross-package imports → repeat.

## Build & test
- `./gradlew assembleDebug` — debug APK.
- `./gradlew testDebugUnitTest` — JVM unit tests. Bare `./gradlew test` rejects `--tests`; use the variant task to filter.
- **Cut a release**: `scripts/release.sh <versionName>` — bumps `versionCode`/`versionName`, prepends notes to `release-notes.txt` (via `$EDITOR`, `--notes <file>`, or stdin), builds the signed APK, commits + tags `vX`, uploads to the Firebase App Distribution `testers` group, and (with `--push`) pushes. `--dry-run` shows the version+notes diff and reverts; needs a clean tree. Full release / function deploy → `plan/CLAUDE_ARCHIVE.md` § Release process.
- **JVM tests**: plain JUnit for pure logic (`TagNormalizerTest`, `PHashTest`). **Compose flow tests** run on JVM via Robolectric (`createComposeRule()` + `@RunWith(RobolectricTestRunner)` + `@GraphicsMode(NATIVE)`) — see `wardrobe/TagFilterBarTest`. Test the **`internal`/stateless `*Content` composables** (`TagFilterBar`, `TagEditScreenContent`, …) with **hoisted state**, not whole screens (screens default their ViewModels to `viewModel()` and do real Drive/Gemini/ML I/O). Resolve display text via `getString(R.string.…)`, not literals.
- **JDK gotcha**: Robolectric can't instrument under JDK 25. Tests are pinned to a **Java 21 toolchain** (`tasks.withType<Test>` in `app/build.gradle.kts` and `core/database/build.gradle.kts`; path in `gradle.properties` → `org.gradle.java.installations.paths` → Homebrew `openjdk@21`) — foojay auto-download is incompatible with Gradle 9. `testOptions.unitTests.isIncludeAndroidResources = true` lets `stringResource` resolve.
- **Instrumented tests** (`androidTest/`, needs device/emulator): `./gradlew connectedDebugAndroidTest`. Prefer Robolectric; reserve instrumented for true device-dependent paths. Cross-tab nav can only be exercised by launching `MainActivity` (tabs are a single `selectedTab` inside the root NavHost's Home destination).

**Placement rule (cohesion over locality).** Put each new or moved file in the package with the **most in-package callers and fewest cross-package callers**.
1. List which existing symbols it calls and which existing files call it.
2. Pick the package that maximises same-package edges and minimises `import com.librelookai.<other>.…` lines.
3. If used by ≥ 2 feature packages with no clear owner, lift to `data/model/` (pure data), `util/` (no-dep helper), or the relevant cross-cutting package. Don't dump in `util/` just to avoid choosing.
4. Avoid creating a new top-level package for a single file — extend an existing one unless ≥ 3 related files justify it.
- Wrong-placement symptom: the new file's `import com.librelookai.…` block is longer than its body, or it adds reverse-direction imports (e.g. `data/model/` importing from a feature package). Move it.

## Dependency injection (Hilt)
- Hilt (KSP) is wired in: `LibreLookAIApp` is the `@HiltAndroidApp` Application, `MainActivity` is `@AndroidEntryPoint`. Versions: Hilt 2.59.2 + KSP 2.3.9 — AGP 9's built-in Kotlin needs Hilt ≥ 2.59 and KSP (kapt is incompatible).
- **`DriveRepository`, `GeminiRepository`, `GoogleAuthManager` are `@Singleton` `@Inject constructor` classes — never construct them by hand.** ViewModels receive them as constructor params (`@HiltViewModel class X @Inject constructor(app: Application, …) : AndroidViewModel(app)`); composables get them threaded down as parameters (`AppContent(activity, driveRepository)`).
- Plain `viewModel()` call sites keep working unchanged — the `@AndroidEntryPoint` activity's default factory is Hilt's, and it falls through to the regular factory for un-annotated VMs. ViewModels with no injected deps stay plain `AndroidViewModel(app)` until they grow one.
- Repository *interfaces* (for fake-based tests) are deliberately deferred to refactor phase 2 — see `plan/refactor.md`.

## Core conventions
- **Identity is `folderId`** — closets map to Drive subfolders. `Location.id` is an ephemeral UUID and must never be used for identity comparisons.
- **File naming triplet**: `{cutoutDriveId}_cutout.webp`, `{cutoutDriveId}_original.webp`, `{cutoutDriveId}.json` — sidecar shares the cutout's Drive ID. Legacy `_cutout.png` / `_original.jpg` items still load (no Drive-side rewrite).
- **Image encoding is centralised in `util/ImageEncoding`** — both cutout and original are written as **WebP** to keep the user's Drive small (target ~1 GB for thousands of items). Quality follows the user's `UserPreferences.imageQuality` tier (Settings ▸ Advanced; BALANCED=lossy q80 default, HIGH=q90, MAXIMUM=lossless), mirrored into the static `ImageEncoding.tier` by `data/session/StaticPreferenceMirrors` (started once in `LibreLookAIApp.onCreate`; same collector mirrors `EmbeddingService.segmenter.foregroundThreshold`). **Never `bitmap.compress(PNG/JPEG, …)` for a stored cutout/original** — call `ImageEncoding.compressCutout`/`compressOriginal`. **Never `name.endsWith("_cutout.png")`** — use `ImageEncoding.isCutoutName` / `isOriginalName` / `cutoutIdFromName` (accept both new + legacy suffixes); build new Drive names with `cutoutNameFor`/`originalNameFor` (or `DriveRepository.CUTOUT_SUFFIX`/`ORIGINAL_SUFFIX`, which now delegate to WebP). Local cache filenames stay opaque keys (decoders sniff magic bytes). Gemini-bound image bytes are labelled by `ImageEncoding.detectMimeType` (sniffs the real format — Gemini accepts `image/webp`), not by file extension. Drive uploads send `image/webp`.
- **Shopping closet** lives in `LibreLookAI/_shopping/`; excluded from `Location` lists, included in cross-closet similarity snapshot.
- **Offline gating**: read `LocalIsOffline.current` and either hide write-path UI or set `enabled = !isOffline`. Every Gemini / Drive-write surface must be gated.
- **Optimistic writes**: mutations (move / delete / tag-edit / bg-queue persist) update in-memory state immediately and write the local cache **before** the Drive call (in the same background coroutine, ahead of the Drive ops); Drive syncs after and rolls back on failure. **Tag-edit sidecar saves and item deletes ride the sync queue** (refactor § 2): `WardrobeViewModel.saveSidecar` writes Room then enqueues a `wardrobe.sidecarSync` `PendingMutation`; the `SyncEngine` (`core/sync`) drains it via `wardrobe/WardrobeSidecarSync.kt`, which re-reads the row's *current* tags/folder at apply time (payload-free — Room is the source of truth), retries transient Drive failures (rows survive process death; catch-up drain on app start/network-regain via `SyncConnectivityCatchUp` in `core/sync` — a process-long `NetworkMonitor.isOnline` collector started from `LibreLookAIApp.onCreate`, the `NetworkMonitor` itself being a Hilt `@Singleton` now — the engine's own 30s→10min backoff re-drain while the process lives, plus a WorkManager backstop — `data/drive/SyncWork.kt` schedules one unique network-constrained `SyncDrainWorker` whenever a drain starts over a non-empty queue, so a process killed mid-queue drains without waiting for the next app start), and stamps the new `sidecarDriveId` onto the Room row — which the derived wardrobe view picks up via invalidation (the old `sidecarSaved`-flow collector is gone; the handler still emits for future consumers). `deleteItems` enqueues a payload-carrying `wardrobe.deleteItem` per item (`wardrobe/WardrobeDeleteSync.kt` — file ids ride along since the row is gone before the drain; retries replace the old fire-and-forget deletes that orphaned Drive files when offline). `moveItemsToLocation` enqueues `wardrobe.moveItem` per item (`wardrobe/WardrobeMoveSync.kt` — carries the from→to pair; retries ~8 attempts before the handler re-homes the Room row back and the `moveRolledBack` collectors undo the UI half). The shopping closet's `deleteItems`/`moveToCloset` reuse the same mutation kinds; a failed shopping→closet move is undone event-style (both VMs collect `moveRolledBack` — there is no failure callback, since a queued retry can complete in a later session). **Every outfit `_outfits.json` save rides the queue too** (all 11 `OutfitsViewModel`/`OutfitsTags` mutation sites): compute the updated list → `persistOutfitFolders(updated, affected)` (mirrors it into the per-folder `OutfitStore` rows under a mutex, enqueues one payload-free `outfit.syncFolder` per affected folder, drains) → `onDone(true)` — so `onDone` means *locally committed + queued*, not Drive-confirmed. **`OutfitsUiState.outfits` and `.wardrobeImages` are *derived*** (refactor § 5 slice 4b), and as of § 5 slice 8 the derivation + save funnel live in a `@Singleton` **`outfit/OutfitsRepository`** (the foundation for the per-screen VM split): the repo owns the cross-closet scope, the store-derived `outfits`/`wardrobeImages` `StateFlow`s (store rows carry resolved `itemIds` — only `folderId` is `@Transient`), the Drive load helpers (`cachedOutfits`/`syncOutfitsFromDrive`/`idToNameAllFolders`) and the `persistOutfitFolders` funnel (+ mutex). **The outfits VM is split 2-way over that repo** (§ 5 slice 9): `OutfitsViewModel` is the **list** VM (grid/selection/delete/loved/calendar-wear + the save mutators Travel/Try-On call — it drives the scope via `repo.setScope` from the closet session and mirrors `repo.outfits`/`repo.wardrobeImages` into `OutfitsUiState`), and `OutfitGenerationViewModel` owns the AI side — composer + prediction share one state machine (`OutfitGenerationUiState`, incl. the tag-suggestion flow; the `OutfitsComposer`/`OutfitsPrediction`/`OutfitsTags` extension files target it). The two VMs never call each other: brand-new saves go through `OutfitsRepository.saveOutfit` (resolves cross-closet `itemNames`, stamps the home folder, fires the scroll one-shot), the scroll-to-outfit `Channel` and the post-edit-save `pendingWearOutfitId` hand-off live on the repo (generation emits, the list mirrors/consumes). Mutators still no longer splice state and the old `refreshWardrobeImages()` after-sync hook is gone. The handler (`outfit/OutfitFolderSync.kt`) re-reads the folder's store rows at apply time (back-to-back edits coalesce) and **refuses to write a never-cached folder** (`OutfitStore.hasFolder` wipe guard — an empty read there means "unknown", and writing `[]` would destroy the user's outfits). No rollbacks: `setOutfitLoved` no longer un-flips on failure, transient failures retry silently. **The wardrobe item cache is Room, and the wardrobe view is *derived* from it** (refactor § 5 slice 4a): `data/local/WardrobeItemStore` (one `@Singleton` shared by Wardrobe / Outfits / Shopping VMs — the old per-folder `wardrobe_cache_*.json` files are seeded into it once on upgrade, then never read again) is observed by two collectors in `WardrobeViewModel.init` that are the **only writers** of `WardrobeUiState.images` (view scope) and `allLocationImages` (all closets + shopping). **Mutations write the store; the UI follows via Room invalidation** — never splice `state.images`. Two in-memory overlays ride the derivation: `transientItems` (import placeholders with synthetic `__importing_*` ids — no Drive file, so no store row) and `imageVersions` (Coil cache-buster, bumped via `bumpImageVersion` whenever bytes change under an unchanged driveId: rotate / reprocess / cutout-fix / WebP convert). A store row without a locally-cached image file is skipped by the mapping and reappears with the next store write after download. **Cache-folder rule**: key every store write off the item's *owning* `folderId`, never the transient active-filter `folderId` (null in All-locations, changes on closet switch) — use the VM helpers (`persistItemToCache` / `addToCacheFile` / `removeFromCacheFile`, suspend), don't rebuild a folder's rows from the whole `state.images`. The store's primary key is the Drive ID, so **an item is homed in exactly one folder** — upserting under a new folder atomically re-homes it (moves can't leave ghosts, and the derived view drops/shows the item on both sides by itself). Tag edits go store-first too: `persistItemTags` + `enqueueSidecarSync` (callers of `saveSidecar` must have written the row first — there is no state rebuild in it any more). Invariants are tested in `data/local/WardrobeItemStoreTest`. **The shopping wishlist view is derived the same way** (refactor § 5 slice 4c): `ShoppingClosetUiState.items` = the store rows under the resolved `_shopping/` folder (single-folder scope fed by the same `state.folderId` collector that publishes into `ClosetSession`), with its own `imageVersions` overlay (rotate/reprocess), sorted `createdTimeMs`-desc to match Drive's listing order. Shopping mutations write the store (upload upserts the raw placeholder row; the queue swaps it for the cutout via `upsert(staleDriveId)`; `moveToCloset` re-homes rows into the target itself, `onMoved` only feeding the wardrobe VM's recently-moved markers; a rolled-back move restores the wishlist via the handler's re-home). Shopping's `saveSidecar` reads the *store row*, not state, but stays a direct Drive write — it does **not** ride the § 2 queue (unlike wardrobe's). **The outfit cache is Room too** (`data/local/OutfitStore`, seeded once from the old `styles_cache_*.json`): rows hold the `Outfit` as opaque Gson JSON keyed by outfit id, so **an outfit is homed in exactly one folder** (the old files duplicated fresh empty-`folderId` outfits into every folder's cache), and reads restore the `@Transient Outfit.folderId` from the row; the create/edit save paths stamp `folderId` so a fresh outfit homes correctly before the next Drive sync. Every mutation funnels through `persistOutfitFolders()` (Room write + `outfit.syncFolder` enqueue — see above). Invariants in `data/local/OutfitStoreTest`. **The remaining JSON caches are Room as well, and their views are derived too** (refactor § 5 slice 4d — store-observing collectors in each VM's `init` are the only writers of `events`/`trips`/`history`; mutators write the store, never splice state): calendar wears in `data/local/OutfitEventStore` (per-folder, keyed by event id, seeded once from `outfit_events_cache_*.json` incl. the legacy `styleId` alias; `OutfitEventsUiState.events` derives from a closet-session scope over `observeFolders`; `OutfitEventsViewModel.persist()` is local-first over the queue — `outfitEvent.syncFolder` via `outfit/OutfitEventSync.kt`, same `hasFolder` wipe guard, keeping the legacy single-target rule: the whole list re-homes into the active folder, atomic since the event id is the primary key), trips in `data/local/TripStore` and try-on metadata in `data/local/TryOnStore` (both single global lists with a one-row seed marker, seeded once from `trips_cache.json` / `tryons_cache.json`; `trips` derives from `observeTrips()` sorted `createdAt`-desc, `history` from `observeTryOns()` through `migrateSource` + a cached-image-file filter — a row without a downloaded image is skipped until Phase 2 fetches it; trip saves/deletes ride the queue as per-trip `trip.save`/`trip.delete` mutations — `travel/TripSync.kt`, payload-free, file resolved by stable `{tripId}.json` name; the derived `trips` flow, the single-flight Drive reconcile and the save/delete funnels live on the `@Singleton` `travel/TripsRepository` since § 5 slice 9 (`TripsViewModel` is a thin UI surface over it); try-on saves/deletes stay Drive-first but `replaceAll` the store so the derived feed follows — both live on the `@Singleton` `tryon/TryOnRepository` since the § 5 slice 9 VM split; try-on **image bytes stay files** in the Drive cache dir — the store holds metadata only). All legacy JSON files are left on disk as a downgrade net. Invariants in the matching `data/local/*StoreTest` suites. Rationale → `plan/CLAUDE_ARCHIVE.md` § Two-phase load / Optimistic writes.
- **Lazy grids**: never leave a persistent `graphicsLayer`/transform on a `Lazy*` container — it makes the grid skip composing items that appear after a data swap ("items missing until you scroll"); gate it behind the active gesture (see `WardrobeZoomableItemGrid`). Give `items`/`itemsIndexed` a stable `key` **and** `contentType`.
- **Gemini calls return `null` on failure** — every caller must degrade gracefully. All calls log via `TokenUsageRepository.recordUsage(...)` with a `UsageCategory`.
- **AI progress overlay is data-driven.** `util/AiProcessingOverlay` (the gold sparkle shown by every AI-trigger surface) collects the global `gemini/GeminiProgress` bus: it shows the **real upload-byte bar** while the request body streams (driven by `GeminiProgress.CountingRequestBody`), then a **time-based wait estimate** asymptoting toward ~95% (Gemini answers in ~20–40s), plus an elapsed-seconds counter (`ai_progress_*` strings). The bus is wired once via the `GeminiProgress.Listener` `EventListener` on `GeminiRepository.http` (call start/upload-end/finish) — no per-call-site changes; it's a single global slot, so an overlapping bulk call (no overlay) may overwrite it harmlessly.
- **Fashion trends are cached, not fetched per call.** `gemini/FashionTrendsCache` wraps the expensive Google-Search-grounded `searchFashionTrends` with a **weekly, location-specific** cache: keyed by normalised region string, served local-disk-first (`filesDir/trends_cache.json`) → shared Drive (`_trends_cache.json` at root, so reinstall / 2nd device reuse it) → only a genuine miss/stale (> 7 days) hits Gemini, then writes back to both. Falls back to a stale entry on Gemini failure. Both outfit prediction & composer go through `OutfitGenerationViewModel.trendsCache.get(region, category)` — don't call `gemini.searchFashionTrends` directly.
- **Calendar wear history is a taste signal.** Each `OutfitEvent` carries a denormalised snapshot taken at wear time (`outfitName`/`outfitTags`/`itemTypes`/`colors`/`aesthetics` + `tempC`/`weatherCode` + `source` (`WearSource.MANUAL`/`AI_SUGGESTED`) + `loved` + `planned`) so the wear stays usable even after the outfit is edited/deleted — every field has a default so Gson back-fills old events via the generated no-arg ctor. `outfit/WearHistory.kt` owns it: `buildOutfitEvent(outfit, imagesById, source, weather, date)` builds the snapshot (future date ⇒ `planned`), `buildWearHistorySummary(events)` condenses it into a wear-weighted prompt block (manual = ×2, loved = +3; recent wears flagged "avoid repeating"; cold-weather lean called out). The prediction, composer **and** travel-packing prompts all append it. `OutfitEventsViewModel.recordOutfit(outfit, imagesById, source, weather)` (not an id any more) + `setEventLoved(eventId, loved)` are the writers; the calendar day sheet has a ❤️ toggle. History reaches the prompts as a **DB read** (refactor § 5 slice 3): `wearHistoryFlow(session, eventStore)` (`WearHistory.kt`) observes the event store scoped by the closet session, `OutfitsViewModel` collects it into `OutfitsUiState.wearHistory` (prediction/composer), and `TravelViewModel` exposes its own `wearHistory` StateFlow for `buildPackingPrompt` — no AppContent mirror, no `OutfitsUiState` threading into the planner. Gated by the `AiConsiderations.history` toggle (default on; `ai_consider_history` row in `ConsidersCard`, and a chip in the travel planner's `AiConsidersChips`). The travel planner also exposes the expert item-tag dimensions (`AiTagChips`, mirroring the composer's `ExpertTagsCard`). `OutfitEventsViewModel.setEventLoved(eventId, loved)` toggles the loved flag on **one** logged wear — the per-wear ❤️ on the calendar **day sheet** (`OutfitEvent.loved`), and the only thing feeding the taste signal's loved weighting. Hides offline.
- **The outfit ❤️ is one favourite, shared across all outfit-centric views.** `Outfit.loved` (persisted in `_outfits.json`, Gson back-fills `false`) is the outfit's own favourite flag, settable *before it is ever worn*, toggled via `OutfitsViewModel.setOutfitLoved(outfitId, loved)` (optimistic; the Drive write rides the sync queue, home folder only — mirrors `setOutfitTags`). It backs the ❤️ on the **outfit list card** (`OutfitCard`), the **fullscreen detail viewer** (`OutfitFullScreenViewer`, top-right) **and the wear-stats tab** (`OutfitWearStatsTab` reads `style.loved`) — so the heart stays in sync everywhere. It is distinct from the per-wear `OutfitEvent.loved` (day sheet), a finer "loved this specific wear" signal. ## Close / back affordance rule
**Position is fixed at top-left/leading; the glyph encodes the relationship.** A hierarchical drill-down that returns to a parent in a back-stack (Settings sub-routes, `ProfileEditScreen`, `TagEditScreen`, `AboutScreen`) uses `Icons.AutoMirrored.Filled.ArrowBack` + `R.string.action_back`. A self-contained modal / fullscreen task that dismisses back to its launcher (capture, similarity, composer, pickers, viewers, planner) uses `Icons.Default.Close` + `R.string.action_close`, always top-left (leading in a header `Row`/`TopAppBar`, or `.align(Alignment.TopStart)` in a `Box`) — never bottom, never a FAB. The dismiss cross's *position* must not change between states of the same screen (`CaptureScreen` keeps its top-left close in both capture and import-FAB modes). `action_cancel`/`action_dismiss` are reserved for non-navigational uses (aborting an in-progress edit, dismissing a banner); chip-remove / text-clear / Edit↔Close toggles keep their own `Close` glyphs and strings.

## Window quirks (Dialog / Sheet / Popup / AlertDialog)
**Every composable that opens its own window** (`Dialog`, `ModalBottomSheet`, `Popup`, `AlertDialog`, `BasicAlertDialog`, and anything nested inside one) severs the locale-overridden `LocalContext` / `LocalConfiguration` chain and reports `WindowInsets.systemBars` as 0.

Rule of thumb:
1. Capture `parentContext` / `parentConfiguration` **outside** the window-opening call.
2. Re-provide via `CompositionLocalProvider` **inside** the content lambda (for `AlertDialog`, inside **each slot lambda** — the outer wrap doesn't reach slots).
3. Use `LocalSystemBarsPadding` (provided high in `AppContent`) instead of `statusBarsPadding()` / `navigationBarsPadding()` inside Dialogs.
4. Sticky bottom rows in fullscreen Dialogs: `effectiveBottom = max(LocalSystemBarsPadding bottom, view.rootWindowInsets systemBars bottom, 48.dp)` (`util/rememberDialogBottomInset`). The converted destinations still use it where the 48.dp floor is the design's minimum clearance — there it's a layout choice, not a workaround.
5. **New fullscreen surfaces are NavHost destinations, not Dialogs** — every former fullscreen-Dialog detail view (trip/outfit/item viewers, the composers, the planner) is a route now; these rules apply only to true dialogs / sheets / popups. Don't wrap a destination's child-sheet *call sites* in context re-providing — under a destination the chain is intact; the sheet itself captures-outside/provides-inside its own window (the no-op wraps left in `OutfitComposerScreen` from its Dialog era were deleted).

Full rationale + reference implementations (`OutfitComposerScreen` slot-dialog helper, `WeatherPickerSheet`/`ClosetPickerSheet` ModalBottomSheet pattern, `MatchPreviewDialog` action row) → `plan/CLAUDE_ARCHIVE.md` § "Compose Dialog quirks". Read it before adding any new window-based UI.

## Monetization (coins + BYOK)
- **Master switch: `billing/ManagedBilling.enabled`** (← `BuildConfig.MANAGED_BILLING_ENABLED`, set from `managed.billing.enabled` in `local.properties`, **default `false`**). Off = BYOK-only release: every coin/purchase/refinancing surface is hidden (AI-credits card + section, Buy-credits packs, coin cost badges, spend confirms, destructive-dialog coin row), the Gemini proxy is never used (`GeminiRepository.isProxyMode`/`isConfigured`), `CreditRepository.isManagedMode()` is false, and `CreditsViewModel` never connects to Play billing. BYOK key entry stays in **Settings ▸ Advanced** (and the bottom of `BuyCreditsScreen`); the key is stored AES-encrypted via Android Keystore (`gemini/ApiKeyStore`, device-local, never synced to Drive). Flip the flag (with a deployed proxy + Play products) to light the coin economy back up with no code change. The Play release ships with it off. First-run onboarding includes a **"Add your Gemini API key"** step (`onboarding_apikey_*` strings; deep-links to AI Studio key + billing pages, paste field, Next soft-blocked until a key is entered) — see Navigation. End-user walkthrough: `docs/GEMINI_API_KEY.md`. **Two tiers**: a free key covers tagging/suggestions; virtual try-on + background removal generate images and need a billing-enabled (paid) key — the old "free key avoids all costs" copy was corrected across `about_byok_*` / `settings_advanced_byok_*`.
- **Pricing is server-authoritative.** Firestore holds `config/pricing` (private: `multiplier` + raw `costs`) and `config/publicPricing` (auth-readable: post-multiplier coin prices). The `recomputePublicPricing` trigger is the only writer to `publicPricing`. The multiplier never reaches the client.
- **Client reads `config/publicPricing`** via `gemini/PricingClient` (Firestore listener + SharedPrefs cache + fallback to `CreditPack.COST_*`). Started once in `MainActivity.onCreate`.
- **Cost UI**: `billing/CostBadge` is a small leading icon (`🪙 N` managed, `~Nk tokens` BYOK, hidden otherwise) — place it as the first child of any AI-trigger button. `ConfirmSpendDialog` + `requiresSpendConfirm()` gate spends ≥ 20 coins or bulks ≥ 5 items (BYOK never gated).
- **402 → typed exception + global event**: `GeminiRepository.throwIf402` parses `{needed, have}`, emits on `billing/CreditsEvents.topUp`, then raises `billing/InsufficientCreditsException`. A single `InsufficientCreditsDialog` observer in `MainActivity` listens and routes "Buy" → Settings — so individual VMs don't manage dialog state. Per-VM catches only reset loading flags and short-circuit bulk loops via a local `creditsExhausted` flag.
- **No-key / failed-call → global `AiNotice`**: `gemini/AiEvents` (mirrors `CreditsEvents`) carries an `AiNotice(kind, reason, canRetry)` where `reason` is a semantic `AiErrorReason` enum — `gemini/` lives in `core/ai` and is `R`-free, so the reason→`R.string` mapping happens app-side in `AppContent.aiErrorMessageRes`. Every repo call funnels through `ensureConfigured(notify)` (emits `NOT_CONFIGURED` when no key/proxy) and `emitFailure(code, body, notify)` (maps 429→`QUOTA`, 400+`API_KEY_INVALID`→`KEY_INVALID`, 403→`PERMISSION` (paid-key), 5xx→`SERVER`, blocked/empty 200→`BLOCKED`, else `GENERIC`). **Emission is gated on `notify`** — only **user-initiated single calls** pass `notify = true` (`tryOnOutfit`, composer `generateText`); automatic/bulk calls stay silent and degrade to `null` as before. A single observer in `AppContent` shows one `AlertDialog`: `NOT_CONFIGURED` → "Set up key" (closes the try-on/composer Dialogs, jumps to Settings tab 5); `FAILED` → reason + "Retry" when the trigger registered one. **Retry** re-runs the *whole* originating op via the `AiRetry.action` holder, which the trigger site sets right before launching (only single user-tapped actions register; bulk leaves it null → reason-only dialog). `buildRequest`'s managed-no-session path emits `FAILED`/`UNAVAILABLE`; methods catch `AiUnavailableException` separately so it isn't double-emitted.
- **Ledger**: every charge/refund/purchase appends to `users/{uid}/ledger/{autoId}` (server-only write, user can read).
- **`verifyPurchase`** validates against the Google Play Developer API before crediting; the service account needs "View financial data" + "Manage orders" in Play Console.
- **Seeding**: `cd firebase/functions && npm run build && node lib/seed.js` writes initial `config/pricing` (defaults in `firebase/functions/src/pricing.ts → DEFAULT_PRICING`); the trigger mirrors to `publicPricing`.
